# 分析原则（必须遵守）
1. 以仓库本身为准，而不是以网络二手评价为准。优先阅读并综合：
   - README / docs / 官网文档
   - 目录结构、核心源码、examples / demos / tests
   - 依赖与技术栈（如 package.json、pyproject.toml、requirements、Cargo.toml、go.mod 等）
   - LICENSE、贡献指南、最近提交与 Release
   - Issues / Discussions 中反复出现的真实问题
   - Star / Fork / 更新频率 / 维护状态（用于判断成熟度，不用于吹捧）
2. 禁止只改写 README。每个关键判断都尽量能回溯到：文件路径、模块名、配置项、命令或文档段落。
3. 不确定就标明「推断」或「文档未写明」，不要编造功能、性能、兼容性和作者意图。
4. 如果无法访问仓库、文档残缺或项目明显不可运行，先说明限制，再给能确定的部分；不要硬写完整评测。
5. 评价要诚实：写清优点、局限、适用边界、维护风险、和同类方案的差异。
6. 默认面向「能动手跑项目」的读者，兼顾：
   - 先快速判断值不值得看
   - 再看懂它解决什么、怎么工作
   - 最后能自己跑起来并迁移到自己的场景

# 先在内部完成分析（不要把这一部分原样当成文章正文）
请先弄清并组织以下信息：
- 一句话定位：它解决什么问题，不解决什么问题
- 目标用户：谁真正该用，谁不该用
- 实现了哪些能力：主功能 / 次功能 / 明确不做的事
- 仓库结构：关键目录与入口文件
- 工作原理：请求/数据/控制流如何走通；如有 Agent、RAG、流水线、插件系统，画出文字流程
- 核心技术：语言、框架、模型调用方式、关键算法/架构模式、外部依赖
- 运行条件：系统、硬件、API Key、账号、环境变量、GPU/内存要求
- 最小可运行路径：从克隆到看到第一个成功结果的最短步骤
- 典型用法：官方示例之外，一个开发者最可能的 2-3 个真实用法
- 优缺点与风险：稳定性、文档质量、生态、安全、许可证、被弃坑可能性
- 同类对比：至少点名 1-2 个相近项目，说明差异（没有把握就少写，不要硬凑）

# 成稿要求
写一篇完整中文文章，Markdown 格式，可直接发到技术自媒体（如公众号、掘金、知乎）。

## 文风
- 像一个真正读过项目、愿意带读者上手的作者，而不是项目官网文案。
- 专业、具体、好读。少空话，少「赋能」「颠覆」「神器」这类无信息量词汇。
- 需要结论时直接给判断，并说明判断依据。
- 代码/命令只保留「跑起来和用起来」真正需要的部分，并注明运行前提。
- 不要出现「作为 AI 语言模型」等元叙述。
- 不要虚构测评数据、运行截图和未发生的踩坑。若你并未实际执行命令，写「按文档整理的启动路径」，不要写成「我已经跑通」。

## 标题与开头
- 先给出 3 个备选标题：信息具体，能看懂项目价值，避免纯情绪标题党。
- 正文开头用 150 字内讲清：这是什么、解决什么痛点、这篇文章能让读者获得什么。

## 正文必须包含以下 6 个核心部分（可作为二级标题，标题可写得更自然，但内容不能缺）
### 1. 有什么用
讲清它解决的真实问题、典型场景、给谁用、不适合谁。用具体场景，不要只罗列形容词。

### 2. 实现了什么
按「核心能力 / 配套能力 / 边界」写。说明它做成了产品的哪一层：库、框架、应用、Agent、脚手架、评测工具等。指出文档承诺和仓库实际能力之间是否有落差。

### 3. 工作原理
用「输入 -> 关键处理步骤 -> 输出」把主链路讲清楚。
如有必要，用 Mermaid 或清晰分步说明架构。
重点解释：为什么这样设计、关键模块如何协作，而不是名词堆砌。

### 4. 核心技术
写技术栈、关键依赖、关键抽象（如插件、工作流、工具调用、记忆、检索、调度等）。
每个技术点都回答：它在本项目里承担什么角色，而不是科普该技术本身。

### 5. 怎么跑起来
给出一条「最小可运行路径」，按顺序写：
- 环境与前置条件
- 克隆与安装
- 必要配置（.env、模型、密钥、端口等）
- 启动命令
- 如何验证已经跑成功
- 文档里容易踩的坑（版本、依赖、权限、平台差异、常见报错）
命令必须来自仓库文档或可合理推断的标准用法；有多套启动方式时优先写官方推荐的一种，并提及其他方式。

### 6. 怎么用 / 怎么为我所用
这是全文最重要的部分之一，必须超出官方 Quick Start。至少包含：
- 最值得先试的 1 个官方示例，以及这个示例真正演示了什么
- 2-3 个「读者可以迁移到自己工作里」的用法（例如接入现有项目、替换某个手工流程、做内容生产、做 Agent 工具、做学习实验）
- 可改动的关键配置/扩展点（提示词、工具、模型、插件、工作流、UI、数据源等）
- 二次开发从哪几个文件改起
- 什么情况下该用它，什么情况下该换方案或只取其局部思路

## 正文建议再补上的部分（简短即可，但尽量有）
- 项目快照：作者/组织、许可证、技术栈、成熟度、最近活跃情况
- 优点与局限：各 3 条以内，具体到使用体验
- 适合立即收藏 / 适合观望 / 不建议投入的判断
- 结尾：给读者一个明确下一步（跑 Demo、改某一处、接到自己的场景），并附仓库地址

正文 1800-3500 字。宁可短而具体，也不要注水。
