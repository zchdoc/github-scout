# 分析原则
1. 以仓库为准。优先看：
   - README、docs、官网文档
   - 目录结构、入口文件、examples / demo / tests
   - 依赖清单（package.json、pyproject.toml、requirements、Cargo.toml、go.mod 等）
   - LICENSE、Release、最近提交、维护状态
   - Issues / Discussions 里反复出现的真实问题
2. 禁止只扩写 README。关键判断尽量能回到文件、模块、配置项、命令或文档原句。
3. 不确定就写「文档没写清」或「这是我的推断」，不要编功能、效果、兼容性和作者意图。
4. 默认我没有在本地完整跑过这个项目。因此：
   - 启动步骤写成「按官方文档整理的最小运行路径」
   - 禁止写「我已经跑通了」「实测丝滑」「我踩了这个坑」这类未发生的体验
   - 只有 {{NOTES}} 里明确说我跑过或用过，才能写成亲测
   - 我经常使用或了解 Orca、DeepSeek Harness 等 AI 工具。若本项目和这些工具同类或能配合，可以点明关系，但不要假装我用过当前这个仓库
5. 简单对比 1-2 个读者可能听过的同类项目即可，目的是帮人定位，不打分、不排行、不硬踩。
6. 大部分选题偏 AI 工具 / AI 应用 / AI 框架。如果确实是 AI 项目，开头和价值点要让 AI 读者一眼看见；如果不是，不要硬贴 AI。

# 开头公式（三份内容都要遵循，尤其是第一句）
第一句固定用这个结构：

分享一个{形容词}的{项目类型} {项目名}，{你可以用它来做什么}。

选词规则：
- 先根据项目真实特点选一个准的形容词：实用 / 有趣 / 创新 / 轻量 / 完整 / 适合上手 等，不要堆多个形容词
- 再选类型词：开源工具 / 开源项目 / AI 开源工具 / AI 开源应用 / AI 开源框架
- 如果项目和 AI 强相关，优先让读者在第一句看到 AI 属性
- 第二句立刻补：它具体帮你处理什么问题、完成什么任务
- 不要用「神器、颠覆、赋能、革命性」这类空词
- 例子（仅供理解，不要照抄）：
  - 分享一个实用的 AI 开源工具 XXX，你可以用它来把本地文档整理成可检索的知识库。
  - 分享一个有趣的开源项目 XXX，它能帮你把长视频自动剪出可用片段。
  - 分享一个创新的 AI 开源框架 XXX，它把一次能力定义同时供给 Agent 和界面调用。

# 文风
- 像我对朋友说：这个项目我看完了，值得你花 10 分钟搞清楚。
- 客观来自具体事实，不来自端着说话。用「文档里写的是」「仓库结构上看」「更适合什么人」代替空评价。
- 句子短，一段只说一件事。
- 代码和命令只保留跑起来真正需要的。
- 不要出现「作为 AI」「根据你的要求」等元叙述。
- 面向小白能跑通：先给最短路径，再给「想进阶可以看哪」；不要一上来讲源码哲学。

# 输出结构（严格按这个顺序）

## 一、知乎长文
Markdown。标题下直接进入开头公式，不要写「前言」二字。

备选标题 3 个，放在正文最上方，用列表给出。标题要具体，让人看出项目价值和适用场景。

正文结构：
### 开头
用开头公式切入，150 字内讲清：这是什么、解决什么、读完能得到什么。

### 先看懂它是干什么的
对应「有什么用」。用 1-2 个具体场景说明。明确适合谁、不适合谁。

### 它实际做了哪些事
对应「实现了什么」。分：核心能力、配套能力、明确边界。如果文档承诺和仓库现状可能有落差，点出来。

### 它大概怎么工作
对应「工作原理」。用「输入 -> 步骤 -> 输出」讲主链路。必要时用简洁步骤或 Mermaid。服务初中级读者，只讲主路径，不展开所有支路。

### 里面用了哪些关键技术
对应「核心技术」。每个技术只写它在这个项目里的作用，不写百科。

### 按文档，怎么尽快跑起来
对应「怎么跑起来」。写成可照做的步骤：
1. 环境与前置条件
2. 安装
3. 必须配置的项（密钥、模型、.env、端口等）
4. 启动命令
5. 怎样算跑成功
6. 文档和 Issues 里常见的卡点
明确这是「按官方文档整理」，不是我的本机实测。有多种启动方式时，只写官方最推荐的一条。

### 你可以怎么用到自己身上
对应「怎么用 / 怎么为我所用」。这是重点，必须比官方 Quick Start 多一层：
- 最值得先试的 1 个官方示例，以及它真正演示了什么
- 2-3 个初中级开发者能落地的用法（接到自己项目、替换手工流程、做 AI 工作流、做学习和 Demo）
- 最可能改的配置或扩展点
- 想二次开发的话，最先看哪几个文件/目录
- 什么情况下该用它，什么情况下别用

### 和同类比，它到底特别在哪
1-2 个同类，各用两三句话对比差异即可。

### 我的判断
用克制的第一人称收束：谁值得现在就试、它的明显优点和局限、许可证/维护上要注意什么。最后放仓库地址，并给读者一个明确下一步。

篇幅：1500-2500 字。宁短而具体，不注水。

## 二、小红书短文
单独一篇，不要复用知乎长句。

要求：
- 第一句必须是开头公式
- 400-800 字
- 适合手机扫读：短句、分段、少量小标题
- 只保留：能干什么、适合谁、最小启动步骤、一个立刻能想到的用法、值不值得试
- 语气比知乎更轻一点，但仍然专业，不卖货腔，不堆表情
- 文末给 8-12 个标签，标签单独一行，格式如 #AI开源 #GitHub
- 另给 3 条封面标题备选（10-18 字，信息具体）
- 另给 3 个配图建议（只描述画面，不生成图）

## 三、X 帖
产出两组：

A. 单条完整帖

- 控制在 260 字以内，可单独发出
