# 第一部分：仓库分析报告（供作者核对，不发布）

## 调研步骤（必须实际访问仓库，不得凭印象作答）
1. README 与 docs：定位、功能、安装和使用说明
2. 目录结构：核心模块、入口文件、配置文件
3. 依赖清单（package.json / requirements.txt / pyproject.toml / go.mod / Cargo.toml 等）：技术栈和关键依赖
4. 核心源码：至少读入口文件和 2-3 个关键模块，弄清数据流和调用链；仓库很大时，优先读入口、核心抽象和最能体现设计思路的部分，并说明你读了哪些文件
5. 运行相关文件（Dockerfile / docker-compose / Makefile / .env.example / CI 配置）：确认真实的运行方式
6. 项目状态：License、最近提交时间、最新 Release、Star 数、Issues 中的高频问题
7. 1-3 个同类项目，用于横向对比

## 报告结构
1. **项目速览**：名称、一句话简介、技术栈、License、Star、最近更新、活跃度
2. **有什么用**：解决什么问题、面向谁、典型场景
3. **实现了什么**：核心功能清单（标注亮点与基础能力）、与同类项目的差异
4. **工作原理**：整体架构与数据流，标注对应的文件路径和关键函数
5. **核心技术**：关键技术选型、设计取舍，以及 1-2 个最值得学习的设计点
6. **怎么跑起来**：环境要求、安装、配置、启动命令、常见坑
7. **怎么用**：2-3 个上手用例、可集成的场景
8. **优缺点与适用边界**：适合谁、不适合谁、风险（维护停滞、License 限制、安全隐患等）
9. **综合判断**：是否值得投入时间，给出理由
10. **信息来源与置信度**：列出你实际读过的文件；未能访问或不确定的内容单独标出

规则：所有事实必须来自仓库或可核实的来源；无法访问的内容要明说，不要编造；命令若来自你的推断而非文档，必须标注"推断"。

## 内容结构

2. 实现了什么

这不是 README 的转述。要有你从源码中得出的真实理解，要有取舍分析和实用建议。

## 写作要求
- 语言：{{中文}}
- 风格：没有固定腔调。根据项目特点自行选择最合适的口吻（严谨、轻松、吐槽均可），全文保持一致。避免"赋能""闭环""颠覆性"等空话和 AI 腔。
