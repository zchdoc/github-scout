# 第一步：调研（写作之前必须完成）
请实际访问仓库，按以下顺序收集信息，不要凭印象或猜测作答：
1. README（及 docs 目录）：项目定位、功能、安装和使用说明
2. 目录结构：识别核心模块、入口文件、配置文件
3. 依赖清单（package.json / requirements.txt / pyproject.toml / go.mod / Cargo.toml 等）：确定技术栈和关键依赖
4. 核心源码：至少阅读入口文件和 2-3 个关键模块，弄清楚数据流和调用链
5. 运行相关文件（Dockerfile / docker-compose / Makefile / .env.example / CI 配置）：确定真实的运行方式
6. 项目状态：License、最近提交时间、Release 版本、Star 数、Issues 中的高频问题
7. 同类项目：找出 1-3 个可比较的项目，用于横向对比

# 第二步：写作
文章必须包含以下 6 个部分，用清晰的小标题组织：

## 1. 有什么用
- 用一两句话说清它解决什么问题、面向谁
- 用具体场景说明"没有它时有多痛，有了它有什么不同"

## 2. 实现了什么
- 核心功能清单，按重要性排序，说明哪些是亮点，哪些是基础能力
- 与同类项目的差异化对比（可用表格）

## 3. 工作原理
- 用通俗语言讲清整体架构和数据流，可用文字流程图或 Mermaid 图
- 结合你在源码中看到的实际模块、文件和关键函数来讲，标注对应的文件路径

## 4. 核心技术
- 列出关键技术栈和设计思路，说明"为什么这样选"和"有什么取舍"
- 挑出 1-2 个最值得学习的技术点或代码设计，深入讲解，必要时贴精简的关键代码片段

## 5. 怎么跑起来
- 给出从零到跑通的最短路径：环境要求、安装、配置、启动命令
- 命令必须来自 README 或配置文件，如果你根据源码做了补充或推断，请标注
- 列出容易踩的坑（如依赖版本、API Key、端口、网络问题）以及对应的解决办法

## 6. 怎么用 / 怎么为我所用
- 给出 2-3 个上手用例，包含具体的操作示例
- 说明它可以如何集成到读者自己的工作流、产品或学习中
- 优缺点和适用场景：明确说明适合谁、不适合谁、什么情况下别用
- 你的综合判断：是否值得投入时间，给出理由

# 写作要求
- 风格：专业但不晦涩，有观点、有节奏，像一位有实战经验的技术博主在分享。避免"赋能""闭环""颠覆性"等空话和 AI 腔。
- 开头：用一个具体的痛点或场景吸引读者，不要用"随着 AI 的发展……"这类套话。
- 标题：给出 5 个备选标题，风格各异（干货型、悬念型、数据型等）。
- 篇幅：约 {{3000}} 字，代码和图表另计。
- 排版：使用 Markdown，小标题清晰，重点内容加粗，段落简短，适合手机阅读。
- 结尾：总结要点，并加一句引导读者评论、提问或分享自己使用经验的互动语。

# 准确性与诚信规则
1. 所有事实（功能、数据、命令、版本、Star 数）必须来自仓库或可核实的来源，不确定的内容不要写。
2. 你没有亲自运行过项目，因此不要写"我实测……"之类的话。涉及运行效果的部分，请写成"按文档应当……"，并在文末列出"需要作者亲自验证的清单"。
3. 引用他人内容时保持简短并改写，不要大段照搬 README 或其他文章。
4. 发现项目的缺陷、风险（如维护停滞、License 限制、安全隐患）时，如实写出。
