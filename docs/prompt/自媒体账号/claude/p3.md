# 第一部分：仓库分析报告（供作者核对，不发布）

## 调研步骤（必须实际访问仓库，不得凭印象作答）
1. README 与 docs：定位、功能、安装和使用说明
2. 目录结构：核心模块、入口文件、配置文件
3. 依赖清单（package.json / requirements.txt / pyproject.toml / go.mod / Cargo.toml 等）：技术栈和关键依赖
4. 核心源码：至少读入口文件和 2-3 个关键模块，弄清数据流和调用链；仓库很大时，优先读入口、核心抽象和最能体现设计思路的部分
5. 运行相关文件（Dockerfile / docker-compose / Makefile / .env.example / CI 配置）：确认真实的运行方式，并判断最省事的上手路径（如有 Docker 或一键脚本，优先推荐）
6. 项目状态：License、最近提交时间、最新 Release、Star 数、Issues 中的高频问题
7. 1-2 个最相近的同类项目，用于简单对比

## 报告结构
1. **项目速览**：名称、一句话简介、技术栈、License、Star、最近更新、活跃度
2. **项目类型判断**：实用工具 / 有趣项目 / 创新项目 / AI 工具 / AI 应用 / AI 框架 / 其他，并说明是否与 AI 相关及具体关联点
3. **有什么用**：解决什么问题、面向谁、典型场景
4. **实现了什么**：核心功能清单（标注亮点与基础能力）
5. **工作原理**：整体架构与数据流，标注对应的文件路径和关键函数
6. **核心技术**：关键技术选型、设计取舍，以及 1-2 个最值得学习的设计点
7. **怎么跑起来**：环境要求、安装、配置、启动命令、预期结果、常见坑；标明每条命令来自文档还是你的推断
8. **怎么用**：2-3 个上手用例、可集成的场景
9. **简单对比**：与 1-2 个同类项目在定位、上手难度、能力范围上的差异，用来说明本项目的特点
10. **优缺点与适用边界**：适合谁、不适合谁、风险（维护停滞、License 限制、安全隐患、需要付费 API 等）
11. **综合判断**：是否值得投入时间，给出理由
12. **信息来源与置信度**：列出你实际读过的文件；未能访问或不确定的内容单独标出

规则：事实必须来自仓库或可核实的来源；无法访问的内容要明说；不要编造。

# 第二部分：长文（1800-3500 字，可直接发布到知乎，也可贴入 X 长文）

## 开头（固定句式，按项目类型选词）
第一句必须是这个结构：
"分享一个［形容词］的［开源项目/开源工具］［项目名］，它可以帮助你［核心用途］。"

选词规则：
- 实用工具：用"实用的"，例：分享一个 实用的 开源工具 xxx，你可以用它来处理 xxx 问题。
- 有趣项目：用"有趣的"，例：分享一个 有趣的 开源项目 xxx，它可以帮助你实现 xxx。
- 创新项目：用"创新的"，例：分享一个 创新的 开源项目 xxx，它能为你提供 xxx 解决方案。
- AI 相关项目：第一句必须点出 AI 属性，例：分享一个 AI 驱动的 开源项目 xxx，它可以帮你实现 xxx / 管理 xxx。
- 都不贴切时：根据项目特点自选形容词。

形容词必须有依据，不能夸大（只有真正有新意时才用"创新的"）。第一句之后，用第 2-3 句给出一个具体的痛点、结果或反常识的事实作为钩子，不要用"随着 AI 的发展……"这类套话。

## 正文结构
用清晰的小标题覆盖以下 6 个部分：
1. 有什么用
2. 实现了什么
3. 工作原理
4. 核心技术
5. 怎么跑起来（篇幅要给足，这是读者最关心的部分：前置条件 → 安装 → 配置 → 启动 → 预期结果 → 常见坑与解决办法）
6. 怎么用 / 怎么为我所用（含简单对比、优缺点、适用场景、综合判断）

不是 README 的转述。要有你从源码中得出的理解、取舍分析和实用建议。简单对比控制在一个小表格或几句话内，目的是帮读者理解项目特点，不要写成竞品大战。

## 口吻
- 个人号视角，但克制而专业：可以用"我"，观点要有依据，比如"我读了它的 xx 模块，发现……"。
- 可以给出明确判断，包括"不推荐"的情况，但不要夸张、吹捧或贬低。
- 避免"赋能""闭环""颠覆性"等空话和 AI 腔。
- 段落短，一段一个意思，适合手机阅读；用小标题和加粗突出重点。
- 代码只贴最关键的精简片段，并用一句话说明它为什么重要。
- 结尾用几句话总结，再加一句邀请读者留言、提问或分享使用经验的话。

## 关于"我"的真实性（重要）
- 若实测情况为"未实测"：不要写"我跑了 / 我实测"。用"我读了仓库和文档后的判断"、"按文档，跑起来应该是……"、"从代码看……"。
- 若我提供了"已实测"或"曾长期使用"的信息：只能使用我给出的体验，不要自行扩写细节。
- 无论哪种情况，都不要编造性能数据、耗时、截图内容或使用感受。
